# Known issues and verified behaviour

What was checked, against which server, and when. For what is not built yet,
see [ROADMAP.md](ROADMAP.md).

Nothing here is pending. This is not a list of unknowns but of things worth
knowing — where Stalwart departs from a spec, where a setting has to be turned
on for a feature to work, and what Gilbert deliberately does not do.

Each entry names the server it was exercised against, and the date; a behaviour
carrying an earlier version was checked against that one and has not changed
since, which is what the version and the date are for. The newest server the
entries below name is **0.16.22**, the release this build follows.

**0.16.21** was exercised by hand — mail, calendar and contacts — including
editing one occurrence of a recurring series through the interface and
confirming the rest of the series stayed where it was. Four things it does that
a client has to get right are covered below: an occurrence identified by its
recurrence id, `Calendar/get` and `AddressBook/get` returning every property
when none are named, EventSource advertising its ping interval in seconds, and
a calendar write that asks for scheduling messages refused when the account
may not send them.

Entries keep saying what was checked and when, because a claim of live
verification can be wrong: the 0.16 registry path reads as verified live only
when the capability is looked for where Stalwart advertises it, and a look in
the wrong place means it has never run at all.

An entry citing a live **0.15.5**, on 2026-08-25 or earlier, records a finding
about Gilbert rather than about the server it was made against — a byte cap
that applies, a flow that works the same way. Stalwart 0.15 is not supported.

- **All ten translations have never been read by anybody who speaks them.** They were produced by AI against standard dictionaries rather than by speakers — German, Spanish, French, Italian, Dutch, Portuguese (Brazil), Russian, Ukrainian, Simplified Chinese and Japanese, which with English makes eleven languages in the picker — and every one of the ten is marked **Beta** in the picker, with that stated in Settings beside a link for reporting anything that reads wrongly. This is the entry that matters most on this page, because it is the one thing here that cannot be closed by testing: a translation can be complete, consistent, pass every check, and still read like a machine wrote it, and nobody on this project can tell which. What *is* verified is the machinery around them. A missing key renders its English source, so a bad line can simply be deleted; a stale key — one whose English source is gone — is caught by `npm run i18n:check` rather than sitting in the file looking correct and never being looked up. Plurals are asked of `Intl.PluralRules` rather than assumed, which is why Russian and Ukrainian carry three forms and Japanese and Chinese carry one; supplying `one` for Japanese would have been filling in a distinction the language does not draw. Confirmed live on the deployed instance (2026-08-31) against a 6,289-message mailbox: role folders localise and the ~20 custom folders keep the names their owner gave them, dates and the calendar follow the language, and 6,289 renders as *6289 листувань* — the genitive plural a number ending in nine takes, which puts the plural machinery on a real message count rather than a hand-picked value.

- **`npm run i18n:coverage` counts what it can see, and a string it cannot see renders English however many catalogues ship.** It reads JSX text; a string that reaches a reader through a call is not JSX text, and none of these are: a `toast.error(...)` argument, a `confirmDialog({ title, confirmLabel })` prop, a `title=` or `aria-label=` attribute, a template literal, and a label computed rather than spelled. The calendar's own view switcher is the shape of that last one — `v[0].toUpperCase() + v.slice(1)` is correct English and untranslatable anywhere else, while **Day**, **Week**, **Month** and **Agenda** are in all ten catalogues — so it spells its four labels out and calls them. `npm run i18n:check` has a second half (`scripts/i18n-literals.mjs`) that accepts a string wrapped where it is written *or* present as a catalogue key — the constant-table convention, where `SECTIONS` holds `label: "About"` and the render site calls `t(s.label)` — and refuses one that is neither, because that is a string no catalogue can translate however many languages ship. It finds strings a hand sweep does not. Worth recording as a general lesson rather than an i18n one: a coverage number measures the thing it can see, and the strings it cannot see are exactly the ones nobody is checking.

- **A contact photo has to be a `data:` URI; a `blobId` in a card's `media` is refused.** RFC 9610 lets JMAP put a `blobId` in a JSContact `Media` object, and this client uploaded the photo and saved it that way — which the mock accepted, so every test passed and the write only failed once it reached a real server. Stalwart does not take it: **confirmed live on 0.16.22 (2026-09-16)**, a `ContactCard/set` carrying `media.*.blobId` fails with `invalidProperties` on `media`, "blobIds in media is not supported.", and the whole call goes with it. The RFC 9553 `uri` form holding a `data:image/jpeg;base64,…` value is accepted on create and on update and comes back unchanged; a 134 KB one was accepted. Photos are saved inline (`withPhoto` in `web/src/lib/contacts.ts`), a card's other media — a logo, a sound — is left as it was, and a `blobId` a card already carries is still read back through the proxy. The mock refuses a `blobId` the same way, pinned by `server/src/mock/contact-photo-media.test.ts`.

- **A download honours a byte range but says nothing about it, and a range past the end is not a 416.** Stalwart answers a single `Range` with a 206 and its `Content-Range`, and sends no `Accept-Ranges` — **confirmed live on 0.16.22 (2026-09-16)** — so the proxy advertises `bytes` itself, which is what a PDF viewer needs before it will page through a file instead of pulling all of it. The same check found the other half: a range the server cannot serve comes back as the **whole file with a 200**, never a 416, so a viewer that asks for one byte too many gets the file rather than an error. The mock answers ranges the same way and sends no `Accept-Ranges` either, pinned by `server/src/blob-ranges.test.ts`. Server-side `ContactCard/changes` reports creates, updates and destroys exactly, which the contacts store's sync relies on (same check).

- **A compressing hop in front of Stalwart truncates a blob download, and nothing says so.** Node decompresses a gzip response before the code ever sees the body, but leaves the `content-length` header describing the *compressed* bytes. Copying that header onto the longer body forwarded makes the browser stop reading exactly that many bytes in and call the download complete. The threshold a proxy compresses above is what makes it look like a race — the case is #76, a Coolify deployment whose Traefik compress middleware engages above 1 KiB: filter rules one and two are fine and the third pushes the script past it, so it comes back cut off mid-rule, 384 bytes of a 1.3 KB script. It is not what the save guard catches: a truncated script is neither unknown nor empty, so the "refuse to save from a baseline we could not read" guard does not fire — the script parses, just with rules missing, and the next save writes the short version back over the real one. Every blob download shares the fault, not just Sieve: message source, vCards, signature HTML, attachments being forwarded, and the `settings.json` sync. Settings degrade honestly — a truncated file fails `JSON.parse`, which is caught and leaves the local cache in charge — so settings stop syncing between devices instead of being overwritten. The proxy therefore asks upstream for `identity` and, for a hop that compresses anyway, forwards no length at all rather than one describing different bytes. The image proxy needs none of that: it uses `node:http` directly, sends no `accept-encoding`, and never decompresses. The save path does not trust the transport either: a script is checked for completeness against the shape the generator emits — every `# rule:` comment parses, every enabled rule has an `if` and a closed body below it, every block ends with a blank line — and saving refuses on anything short, as does the rule editor, which reports the script as unreadable rather than showing the rules that happened to parse. The check is structural rather than a re-serialize-and-compare, so a script written with a different serializer is still editable; refusing over a changed byte would be the worse bug. It catches a cut at every offset except the end of a complete rule block, which is a legitimately shorter script and indistinguishable from one in the bytes alone — that residual is what the proxy's `identity` request covers.

- **Delete all spam destroys, and does not pass through Deleted Items** — this is the point of the feature and the thing worth checking on a real server, since a folder that empties into another folder has solved nothing. `Email/set destroy`, walked a page at a time so it survives `maxObjectsInSet` the way emptying Deleted Items has to. **Confirmed live on 0.16.19 (2026-08-26)**: Junk Mail emptied and Deleted Items stayed empty afterwards. There is no undo, which is why all three entry points share one dialog that says so. Only Deleted Items and Junk Mail can be emptied this way, enforced in the store rather than only hidden in the menus. **In a group mailbox this is refused entirely for everybody but an installation administrator** (ADR 0015), and so are the other two things that end a message for good — a destroy out of Deleted Items or Junk Mail, and deleting a folder together with its mail. A group's Deleted Items and Junk Mail are therefore real folders members fill and cannot empty, which is the one place an installation has to watch the group's quota rather than the members tidying it. The rule is a convention this client keeps and **not a boundary**: another JMAP client, IMAP, or the mail server's own administration destroys the same mail, so an installation that needs the guarantee rather than the convention has to take it up in the mail server, where the membership model is the thing to change. What makes it a convention is written in ADR 0015 — there is no rank inside a group for the server to read, and its destroy permission is held per role, so withdrawing it would close the holder's own mail too.
- **Sharing a mail folder is accepted and does nothing.** `Mailbox/set` with a `shareWith` map is applied, `Mailbox/get` reads it back, and the folder never appears for the account it was shared with — **confirmed live on 0.16.19 (2026-08-27)** with a folder shared read-only to another account on the same server, which never saw it. Stalwart's own sharing documentation lists calendars, address books and file storage; mail folders are not among them. Nothing reports a failure at any point, which is the whole problem: the share is stored, so a client that trusts what it reads back shows it as live for ever. The entry point is not offered. A folder that is *already* shared still offers **Stop sharing**, because a share nobody can see is exactly the one you want to be able to clear, and there is no other way to. File sharing is unaffected and works end to end.
- **Address book sharing works.** Stalwart documents address books as shareable, and nothing about it is known to be wrong. Shared books appear in the Contacts pane under "Shared with me" rather than behind an account switch, and their contacts are offered when addressing a message.
- **Stalwart lets a sharee subscribe to a shared calendar but not a shared address book.** Subscribing is a write to the *owner's* account -- `isSubscribed` lives on the collection, not on the reader -- and 0.16.19 refuses it for a book shared read-only: `AddressBook/set` answers successfully with the id in `notUpdated`, `forbidden`, *"You are not allowed to modify this address book."* The identical `Calendar/set` on a shared calendar is accepted. **Confirmed live on 0.16.19 (2026-08-27)** from a second account holding both shares, which is the only place it shows: from the owner's own account the write succeeds and everything looks fine. So Gilbert asks the server first, because a preference the server holds is one every client agrees about, and keeps the answer in its own synced settings (`addedShares`) when the server will not. Two things are worth remembering here: the refusal arrives as a *successful* response, so code that ignores `notUpdated` sees nothing wrong and the button does nothing; and it is invisible from the owner's account, so finding it takes two browsers signed in as two accounts. The mock refuses the same write for the same reason, since a mock that accepts it agrees with a belief the server does not hold.
- **A mailbox's `shareWith` is not returned unless a client asks for it by name.** A `Mailbox/get` with no `properties` comes back without the field at all — not null, not empty, absent — **confirmed live on 0.16.19 (2026-08-27)** against a folder genuinely shared with another account on the same server, and still so on **0.16.21 (2026-09-06)**. Calendars and address books are the other way on 0.16.21: `Calendar/get` and `AddressBook/get` hand over every property when none are named, `shareWith` among them (live on 0.16.21, 2026-09-06). Gilbert names its properties on all three, so a share is readable on any 0.16 rather than only the newest. The omission is silent, and every consequence of it is: nothing is badged as shared, "Stop sharing" does not appear because nothing looks shared, and the share dialog opens on *"not shared with anyone yet"* over a live share — so the one screen that exists to manage sharing is the one most confidently wrong about it. Mail folders matter in a way of their own: sharing one is withdrawn, and the only way to clear a share that already exists is a **Stop sharing** entry that appears when a folder looks shared — so without the property the escape hatch for the exact situation it exists for is invisible. The mock omits it for a mailbox the same way, since one that hands it over unasked lets a client that never asks look correct everywhere except against a real server.
- **Stalwart's `x:PublicKey` registry works, and Gilbert deliberately does not expose it.** A Settings section for it is not built (PR #67, PR #285), for a reason that has nothing to do with the server: **nothing in Gilbert signs, encrypts, decrypts or verifies with a key**, so a page for managing them is furniture rather than a feature. It ends up telling the reader, in its own footnote, that adding a key does nothing. The registry is written up here rather than in [ROADMAP.md](ROADMAP.md) because what follows is established fact about Stalwart that cost a live probe. Everything below was **confirmed live on 0.16.20 (2026-09-05)** from a normal account with no administrative rights, and the full round trip — create, read back, rename, patch, destroy — succeeded for both formats.

  - **An ordinary user may read *and* write their own keys**, whatever the permissions table says: Stalwart documents every `sysPublicKey*` permission as administrative, and the server granted them anyway. A create carrying a malformed key was refused with `invalidProperties` naming `key` rather than `forbidden` — a rejection of the key, not of the person. Had the documentation been right, such a feature would have been useless to everybody but an administrator.
  - **It takes S/MIME certificates as well as OpenPGP keys, and parses both.** A self-signed X.509 certificate carrying `emailProtection` and an `email:` SAN registered, read back and destroyed cleanly, and a malformed one is refused by a decoder of its own: *"Failed to decode X509 certificate: BER decoding error: Expected Tag { class: Universal, value: 16 } tag…"*. Worth checking rather than assuming, because every *other* message the registry returns names OpenPGP — including for input that is not OpenPGP at all — so the server reads as though OpenPGP were the only format it knows. It is not.
  - **A key can parse perfectly and still be refused, and says something different when it is.** A sign-and-certify OpenPGP key with no encryption subkey — which is what `gpg --quick-generate-key` produces — comes back *"Could not find any suitable keys in OpenPGP public key"*, distinct from the parser's *"Failed to decode OpenPGP public key: Malformed packet: Malformed CTB…"*. Any client showing these must keep them apart: one says paste it again, the other says the key needs an encryption subkey and no amount of care with the clipboard will help. Certificates have no equivalent trap, since one issued for email use has key encipherment by construction.
  - **`emailAddresses` comes back as `{}` when empty** — an object, where a JMAP list property should be an array. Nothing fails loudly: it is a plain `Get` response that type-checks against a hand-written interface and then throws in `join()` while a list renders. A client must check the shape rather than trust the type.
  - **A create answers with the id alone**, no `createdAt`, so anything that reads the date back out of the create response gets `undefined`. **Patching `key` on an existing entry is allowed**, which is worth knowing and probably worth not doing: replacing a key by adding one and removing the old keeps `createdAt` meaning what it says.
  - **`expiresAt` is the registry's own field and is not derived from the key.** A certificate valid for a year registers with `expiresAt: null`. Reading the real date means parsing the certificate, and a date a client extracted would disagree with the server's field the moment the two ever differed.

- **Signature checking is done here, and its trust model is deliberately small.** Stalwart does not verify S/MIME or OpenPGP signatures and exposes no result for one, so Gilbert does it in the browser: raw message, MIME split, PKCS#7 parse, WebCrypto. What is worth knowing is what it does *not* do, because the gap is a design choice rather than an omission. **No chain of trust is validated** — a browser has no system trust store, no CA bundle is shipped, and revocation is not checked — so a verified signature on its own shows only that the sender held the key inside their own message, which anyone can self-sign. What carries the weight instead is trust on first use: the first signed message from an address pins its fingerprint in the account's settings, and a later message signed by a different certificate is reported loudly. That is why the interface never says the bare word "verified", why a first sighting is grey rather than green, and why a changed signer never overwrites the pin. Verified against real `openssl smime -sign` output rather than hand-built fixtures — RSA and ECDSA, plus a tampered copy — because a signed message written by hand only ever agrees with whatever the author believed the format to be.
- **OpenPGP signatures cannot be checked at all, for a reason that is not effort.** A PGP signature carries no key, so verifying one needs the sender's public key in advance, and there is nowhere to get it: `x:PublicKey` holds the *account's own* keys, not correspondents'. Fetching from a keyserver or via WKD would tell a third party who you correspond with each time you opened a message — the same leak the image proxy exists to close — so it is not done. Such a message says so by name rather than failing as an unknown format, and it says *could not check* rather than *did not check out*, which is a distinction worth keeping: one is ignorance and the other is an accusation.
- **Two signature shapes are declined rather than attempted.** SHA-1 signatures are refused outright — one nobody can forge in practice today is still not one to put a tick beside. RSA-PSS is declined because the salt length lives in parameters Gilbert does not read, and guessing wrong would report a perfectly good signature as *bad*, which is a far worse thing to say than "cannot check". Both are shown as uncheckable, not as broken.
- **Read receipts are built here, not by the server** — JMAP has an extension for them, [RFC 9007](https://www.rfc-editor.org/rfc/rfc9007.html)'s `MDN/send`, and Stalwart does not implement it: `urn:ietf:params:jmap:mdn` is not among its capabilities. So Gilbert assembles the `multipart/report` itself and sends it the long way round — raw MIME uploaded as a blob, `Email/import`, then `EmailSubmission` — which is also why the receipt lands in Sent, where it honestly belongs. Non-ASCII parts are base64 rather than `8bit`, so nothing depends on 8BITMIME surviving every hop. There is deliberately no "always send" setting: a receipt confirms to whoever asked that the address is live and when it was read, to an address of the sender's choosing, so each one is a decision. Verified against the mock end to end (upload, import, submit, `$mdnsent`), and **confirmed live on 0.16.19 (2026-08-26)**: a receipt asked for by a real sender was assembled, uploaded, imported and submitted, landed in Sent, and set `$mdnsent` so a second look does not offer to send another.
- **Where 0.16 advertises `urn:stalwart:jmap`** — not where a JMAP client would look, and it decides whether a sign-in is allowed at all. Stalwart builds the session-level `capabilities` from a fixed list (`Session::new`, plus WebSocket) that does not contain this capability, in any 0.16.x; it hands it out per-account instead, so it appears in `primaryAccounts` and in each account's `accountCapabilities`. Reading `capabilities` alone makes every real 0.16 server read as older than 0.16, and that one check drives three things: a server that reads as older takes the self-service credential path 0.16 does not answer — `POST /api/account/auth` is gone, so password changes, 2FA and app passwords fail with "this mail server does not offer self-service credential management" — About reports the wrong generation, and Files take the older code path. Gilbert looks in all three places, covered by tests on each. There is no fallback path for this check to be wrong *into*: getting it wrong refuses every sign-in against a perfectly good server — a loud failure rather than a quiet misrouting, which is the trade of supporting 0.16 alone.
- **HTML signatures** — Stalwart caps a signature at 2047 **bytes** (`value.len() < 2048` on a Rust string, so UTF-8 bytes, not characters). Gilbert compacts pasted HTML, moves images to Files and, if still too large, keeps the full signature in Files behind a short marker; other clients see a text fallback. Confirmed live on 0.15.5 (2026-08-24): oversized, non-ASCII and inline-image signatures all save, and a test message arrived intact at Gmail with the logo inline.
- **An identity's Bcc is deferred to the client by the spec, and Stalwart carries it.** RFC 8621 gives `Identity` a `bcc` property and says the client should add those recipients to the message; Gilbert writes them into the draft's own Bcc field as it opens, so the writer sees the address and can take it off (ADR 0007). **Confirmed live on 0.16.23 (2026-09-24)**: `Identity/set` accepts a `bcc`, `Identity/get` returns it unchanged, and a message submitted from that identity is accepted. The mock answers both the same way.
- **Settings live in the account's Files, not the browser** — a preference kept only in `localStorage` follows nobody between devices. The sharpest case is the default identity: with none set the address that sorts first wins, so a setting made at work is unset at home and mail goes out from an address the recipient might not recognise (#54). The settings are a `settings.json` in the `gilbert` folder in JMAP Files, beside the signature images already kept there — which keeps Gilbert itself stateless: no volume, no database, nothing to back up separately, and the settings are covered by whatever backs up the mail store. `x:AccountSettings` was the other candidate and does not fit; its schema is `locale`/`timeZone`/`description` with no free-form field, and writing it needs `sysAccountSettingsSet`, where the built-in user role carries only the `…Get` half. `localStorage` stays on as a *cache* rather than the source of truth, so the first frame paints from it and the file corrects it a moment later; a browser with no cache shows defaults for that one frame, which is the trade for not gating the whole app on a round trip. Settings that describe *this* screen or browser deliberately stay local — list-pane sizes, density, font size, sidebar state, and the notification toggles, which track a permission the browser grants per-device and would be a claim about somewhere else it cannot make. That split is written as a list of exceptions, so a setting added later syncs by default. Writes are coalesced behind a three-second debounce, since `update()` fires on every frame of a splitter drag, and a tab going away or a sign-out flushes first. The `gilbert` folder is hidden from the Files view, contents and all: hiding the folder alone would be worse than showing it, because the tree attaches a node whose parent is missing to the root, so the signature images kept in that folder would have spilled into the top level. **Confirmed live on 0.16.19 (2026-08-26)**: settings set in Chrome came back on a fresh login in Firefox and in an incognito session, both of which start with an empty cache, so each read the account's file rather than anything local. Confirmed again on the deployed instance rather than only a pre-deployment build. Requires 0.16, which Gilbert requires everywhere — `FileNode/query` cannot see directories before that, and sign-in refuses an older server outright. Two limits worth knowing: conflicts are last-write-wins, and a change made on one device does not reach another that already has Gilbert open until it signs in again.
- **Files on 0.16** — the two fallbacks worth knowing about, and what has actually been exercised on 0.16.19. The shape is 0.16's own: every node carries a `nodeType`, and rights are four separate flags rather than one `mayWrite`. Finding and creating a folder, creating a node with `nodeType`, uploading and downloading its blob, and pointing an existing node at a new one all ran live on 2026-08-26, as a side effect of the settings file; rename, move and delete are **confirmed live on 0.16.19 (2026-08-26)**. Two fallbacks are worth knowing about: `ensureFolder` and `findInFolder` filter on `parentId`/`isTopLevel` alone and match names client-side, since `name` is not a filter Stalwart is known to implement and one it does not know fails the whole query; and a refused filter or sort does not drop the view into fetching every node in the account, which would hide a real fault behind a performance cliff nobody would notice.

- **A destroy of a folder that still holds something is refused without the cascade flag, and the refusal is `nodeHasChildren`.** `FileNode/set` with `{ destroy: [aFolder] }` and no `onDestroyRemoveChildren` on a folder holding a file answers `notDestroyed` with `{"type": "nodeHasChildren", "description": "Cannot delete non-empty folder."}`, and the folder and the file stay. **Confirmed live on 0.16.23 (2026-09-24)**. That is the safe direction and it is load-bearing in two directions: the Files view's delete sends the flag (a folder the reader deleted takes its contents with it), and a **folder merge**'s last step deliberately does not, because a merge destroys a folder it *emptied* and a folder it did not empty must stop the merge instead of disappearing with whatever landed in it between the scan and the last step (ADR 0014). An emptied folder is destroyed either way, and with the flag the descendants go too. The mock models all of it and answers the real type, pinned by `server/src/mock/destroy-non-empty-folder.test.ts`; the refusal reaches the reader as the server's own sentence, never as a folder quietly taking more than they asked for.
- **Self-service credentials** — the registry path is **confirmed live** against Stalwart 0.16.19 (2026-08-25): app passwords created and revoked, password changed, 2FA enabled and disabled, with the browser session surviving the switch to an app password. The mock enforces the same rules the real server does (current password required, password policy, a TOTP code on every request once 2FA is on, app passwords exempt from it). Password changes are refused by Stalwart for accounts backed by an external directory (LDAP/SQL/OIDC); the server's own message is shown when that happens.
- **Scheduled send needs one setting turned on, and says nothing when it is off.** Stalwart advertises the delay in the account's `urn:ietf:params:jmap:submission` capability — `maxDelayedSend: 2592000` (30 days) and `FUTURERELEASE` among its `submissionExtensions`, and note it is the *account* capability, not the session-level one, which is empty. But the MTA only honours a hold when `futureRelease` is set under the session's MTA extensions, and [that setting defaults to `false`](https://stalw.art/docs/ref/object/mta-extensions/). With it off, Stalwart takes the `HOLDUNTIL` parameter, skips the hold and sends the message immediately **without an error** — the capability still says thirty days. So set `futureRelease` (to the longest hold you want to allow) before relying on this; a value shorter than 30 days is fine, and a request past it is refused honestly, with a `forbiddenMailFrom` naming the limit. `npm run dev:mock:no-future-release` reproduces the silent-drop case. Gilbert asks for the delay the way JMAP requires — a `HOLDUNTIL` parameter on the envelope's `mailFrom`, since RFC 8621 makes `sendAt` read-only and server-derived — and files the held message in a **Scheduled** folder, because `onSuccessUpdateEmail` would otherwise drop it in Sent the moment the submission is created. Nothing moves it out when the hold expires, so Gilbert reconciles the folder on the way in: released messages to Sent, cancelled ones back to Drafts. The hold itself is **confirmed against the live 0.16.19** (2026-08-25): a submission carrying a `HOLDUNTIL` ten minutes out came back `pending`, with `sendAt` equal to the time asked for and a `250 2.1.5 Queued` from the MTA, rather than going out at once. Worth repeating that the capability is no evidence either way — it advertises `maxDelayedSend: 2592000` and `FUTURERELEASE` with the setting off. Only a submission tells you. The rest of the journey is **confirmed live too (2026-08-26)**: a hold expired and was delivered, and the **Scheduled** folder reconciled on the way in — a released message moved to Sent, a cancelled one back to Drafts. Nothing in Stalwart does that moving, so if Gilbert is never opened again the message still goes out; it is only the folder that waits to be tidied.
- **Stalwart 0.16 and RFC 8984 disagree about the calendar vocabulary, and the server only says so half the time.** A participant's address lives in `calendarAddress`, not RFC 8984's `sendTo`/`email`; the organizer is `organizerCalendarAddress`, not `replyTo`; and a recurrence is a single `recurrenceRule`, not a `recurrenceRules` array. Addressed the RFC's way, `CalendarEvent/set` **keeps the event and discards the whole participant map without an error** — guests are gone on save and no invitation is ever sent, which is the failure #26 reports. The array form of the rule is refused honestly, with `invalidProperties`, so a client writing the RFC's spelling cannot create a recurring event or read the repeat of one that exists (#30). Gilbert writes Stalwart's names and reads either, and the mock refuses what the real server refuses, since a mock advertising the RFC spelling is precisely how this reaches a live server. Verified against 0.16.19 on 2026-08-25, end to end: participants, organizer and rule all survive a create, an update and a re-read; an invitation to an external Gmail address arrived as an invite card, and the decline came back and was applied to the event (`needs-action` → `declined`, sequence 1). Cancelling the event notified the guest too. Adding guests to an event that had none, and clearing them again with `null`, both work on the update path, as does RSVP — which patches `participants/{key}/participationStatus` (and `participationComment`) rather than sending the whole map. That patch is aimed at the base event, which is the answer people mean: RSVP resolves `baseEventId` first, so the reply answers for the series rather than for one date — a patch aimed at the occurrence would answer for that date alone. Adding a *new* participant by patch is refused as well (`Patch operation failed`), so a changed guest list is written as the whole `participants` property. One more thing to know when reading this code: an expanded occurrence carries a `recurrenceId` but *no* rule of its own, and `baseEventId` is set on everything an expanded query returns — a one-off included, whose own id differs from its base — so neither is a test for recurrence.
- **Free/busy between accounts needs no sharing, and calendar contents cannot be reached at all.** These are the two halves of the same finding, and the second is what makes the first safe. **Confirmed live on 0.16.20 (2026-09-01)** against the deployed instance: `Principal/getAvailability` was called for all seven principals the directory returns, none of whose calendars are shared with the calling account, and every one was answered — no `forbidden`, no error of any kind, from a server that refuses a malformed call instantly. It returns real data rather than a polite empty list: the caller's own principal reported one busy period against the one event in the next sixty days. And a `Principal` carries only `id`, `type`, `name`, `description` and `email` — **no `accountId`** — so there is no handle with which to ask for anybody's calendars. Free/busy is therefore not the weaker of two permissions, it is the only channel between two accounts, and it is open by default. That is the right posture and worth recording, because a client that assumed sharing was a precondition would hide a working feature behind a setting nobody needs to touch. **One thing this did not settle**: the other six principals reported nothing over a nine-month window, which is equally consistent with "those accounts have empty calendars" — likely, since the session reaches one account — and with "an unreadable principal answers with an empty list rather than an error". Distinguishing them needs a second account with an event in it, and until somebody has one, Gilbert assumes the pessimistic reading everywhere it matters: a participant it cannot read is drawn as unknown rather than as free.

- **An override can move an occurrence, and then `start` and `recurrenceId` mean two different times.** The slot stays where the rule put it and only the clock time moves. **Confirmed live on 0.16.20 (2026-08-31)**: one occurrence of a weekly 09:00 series moved to 14:00 came back `start: 2027-06-14T14:00:00` with `recurrenceId` still `2027-06-14T09:00:00`. This is the right behaviour and it is the reason `recurrenceId` is the handle Gilbert holds: it is the one name for an instance that survives a move and a re-resolution, so a mutation can always be resolved from it again. Worth recording because a mock can get it wrong in the other direction — overwriting an override's `start` with the slot time, so a moved occurrence does not move, and per-occurrence *time* editing looks broken against the mock and correct against the server. Asking a real server rather than reading the mock is the only way this kind of disagreement surfaces.

- **An occurrence is identified by its recurrence id, and holding its id across a write stays correct.** Stalwart's expanded ids name the occurrence rather than a position in the series, so writing a `recurrenceOverrides` entry leaves every other id where it was. **Confirmed live on 0.16.21 (2026-09-06)**: five weekly occurrences expanded, the third retitled through its own synthetic id, and all five original ids re-read — every one still resolved, and every one still named its own date, with none `notFound`. A second override written through the interface behaved the same way. Gilbert never mutates an occurrence by an id it is holding in any case: `updateEvent` and `destroyEvent` re-resolve by `recurrenceId` immediately before acting, because a date can leave a series and because the client supports 0.16 as a whole rather than only its newest release. An expanded query's order is not fixed either — the overridden occurrence comes back last — which is why a client sorts by `start` rather than trusting query order. The mock reproduces that stability, and the test suite pins it.

- **A per-occurrence patch made only of inherited properties creates an override that loses the title.** The twelve properties Stalwart drops from a per-occurrence patch are dropped *after* it has decided to write an override, so a patch consisting only of them still writes one — and that override carries the `start` and `duration` the server fills in and nothing else. **Confirmed live on 0.16.20 (2026-08-31)**: `{"privacy": "private"}` aimed at one occurrence answered `updated`, left `privacy` untouched on the series, and left that date with no title at all. A successful response, a silently discarded change, and real data loss on a third property nobody mentioned. Gilbert narrows a per-occurrence patch before sending it and sends nothing when narrowing empties it, on a point of principle — a request whose response could only be a meaningless "updated" is worse than no request — which also prevents this. Worth remembering as the argument for the principle.

- **Recurring events can be edited and deleted one date at a time.** A write aimed at a synthetic id becomes a `recurrenceOverrides` entry rather than a change to the series, so "this occurrence" and "the whole series" are two different things Gilbert asks about before acting. **Confirmed live on 0.16.20 (2026-08-31)** end to end against a five-week series: a legal patch landed on the override with `start` and `duration` filled in by the server; `useDefaultAlerts` was refused with *"This property cannot be modified on a single occurrence."*; a destroy removed one date and left the series; and a base event and one of its instances in the same request were refused together, both ids, with *"A base event and its instances cannot be modified in the same request."* The scope is chosen before the editor opens rather than on save, because it decides which event the form is about — one populated from the master shows the *series'* start date, so editing Wednesday would have offered to move Monday. Two entries below are the sharp edges of this.
- Editable date boxes are always Gregorian and in Latin digits, even for locales whose *display* uses another calendar or numbering system (`fa-IR`, `th-TH`, `ar-EG`) — they keep the locale's field order and separator, but a Buddhist-era year in a text box does not round-trip against the Gregorian calendar grid. Non-Gregorian calendar support is not implemented.
- The account locale is read from `x:AccountSettings/get`, whose permission the built-in user role has, falling back to `x:Account/get` (which needs the admin-only `sysAccountGet`). Both are Stalwart 0.16 methods, and a locale the server will not answer for leaves the browser's own in charge, with the language choosable by hand. Confirmed live on 0.16.19 (2026-08-25), with the capability looked for where Stalwart advertises it; a locale request that is merely refused does not downgrade the detected generation.

- **An agent's first pass anchors at "now", and the server's answer is what makes it.** Every claim starts with an empty `states` map, and the executor asks `Email/changes` (and `FileNode/changes`) with `sinceState: "0"`. Its branch for the answer — `cannotCalculateChanges` or `invalidArguments` — records the account's *current* state and acts on nothing, so a fresh claim serves the mail that arrives after it and never the mailbox it found. **Confirmed live on 0.16.23 (2026-09-24)**: a `sinceState: "0"` query against a mailbox holding mail answers `invalidArguments`, which is that branch, so a new claim starts from "now" rather than firing every enabled rule over the whole mailbox. The test that pins it is the executor's `reconcile` against the mock.

- **An account holds fifteen push subscriptions, and a create past that is refused with `overquota`.** Stalwart's ceiling on `PushSubscription` is fifteen per account, and the refusal is a `notCreated` carrying `{"type": "overquota", "description": "There are too many subscriptions, please delete some before adding a new one."}`. **Confirmed live on 0.16.21 (2026-09-14)** by probing create and destroy directly with an agent credential: the same request — same URL, same type list — was accepted on another account and refused on the sixteenth create on this one. What fills them is the lifecycle rather than any single bug: a client that registers a subscription under an identity it cannot come back with leaves one behind every time that identity dies. The symptom is quiet: the account drops to the per-tab relay, mail is never lost, and the only thing gone is the fast path. Three properties of the server are what a client has to work around, and none is written down anywhere else: a subscription outlives the process that made it, and the only credential that can destroy it is the one that created it; a POST to a URL nobody answers is answered 404 and retried rather than revoked; and a subscription's `url` does not come back on `PushSubscription/get` at all — `url: null` even for a row registered with one (live on 0.16.21, 2026-09-14), so a leftover is recognised by its `deviceClientId`. Gilbert answers all three. The installation carries one identity, `gilbert-<deviceId>` derived from its Stalwart, base path and origin, which survives a restart — so a boot releases the row its predecessor held instead of adding a sixteenth. The browser carries one that survives its own lifetime and releases its registration before making a new one. And a create refused for want of a slot is met by reclaiming the rows a past build left under the same prefix, told apart from a browser's own registration **by the shape of its device id** — this installation derives a sixteen-character identity, a browser makes a random UUID — and never by the types the row asked for, which a client may legitimately change. Two things about this are **not** verified, and are recorded as such rather than assumed: whether an expired subscription frees its slot without being destroyed, which is what "seven days" would mean for a subscription nobody owns — the server's default lifetime for one, not a measured expiry; and what a browser's own row does at the ceiling, where the client now releases the row of another browser that was never verified or is closest to expiring. What **is** verified: a create asking for an `expires` a day out carries it back (live on 0.16.21, 2026-09-14), so the lifetime a row gets is the one the client asked for, and `update` of `expires` is accepted (0.16.22, 2026-09-16), which is what lets a client extend the row it has instead of adding one. `scripts/probe-push-subscriptions.mjs` lists an account's subscriptions, frees the ones wearing a `gilbert-…` device id, and can prove with a throwaway create that the account left `overquota`.

  Two more properties of the same object are read from Stalwart's source at **v0.16.22** (`crates/jmap/src/push/set.rs`, `crates/services/src/state_manager/push.rs`), and both surprise an operator. **A push URL may not point at a local or reserved address** — `validate_push_url` refuses anything but `https`, refuses credentials in the URL, and refuses a host that parses as a non-global IP — so a push service run on the same LAN as the server (a self-hosted `ntfy`, an UnifiedPush distributor on `192.168.…`) cannot be registered, and the reason arrives as an `invalidProperties` on `url` rather than as a delivery that quietly never happens. And **a subscription serves every account its principal is a member of**, not only the one it was created in: the push server registers a verified row for each id in the token's `member_ids()` — the account itself plus its `member_group_ids` — so a member of a group is woken by that group's mail whether or not any client made a decision about that group. It is the reason the per-account payload ADR 0016 owes is a map in one row rather than a row per mailbox.

  **One delivery is two pushes**, also read from the same source: the storage transaction that writes a message broadcasts a `StateChange` (`crates/common/src/storage/transaction.rs`), and the delivery broadcasts an `EmailPush` beside it (`crates/email/src/message/delivery.rs`), and the push client POSTs both to the same endpoint. Which of the two a given subscription receives is decided by its `types` bitmap, and that is what a client has to get right: while it asked for `Email`, every read, flag and move from any client arrived as one more "new mail", and a delivery to an account the subscription describes arrived twice. Asking for `EmailDelivery` instead removes the noise at the source — the bitmap admits no `Email` state change at all, so nothing a read or a move produces can reach the device — and the delivery that carries the reader's own mail arrives as the `EmailPush` that names its sender, because a subscription with an `emailPush` entry for that account is sent one. **What a delivery to a group mailbox does is a different question and is owed rather than answered**: the delivery is degraded to a plain state change there, and nothing read so far says which type that state change wears — if it is not `EmailDelivery`, the bitmap filters it out and the group notification that says "New mail" today stops arriving, silently. That is the fifth item under ADR 0016's debt, and it is why the group case is left as it is here.
